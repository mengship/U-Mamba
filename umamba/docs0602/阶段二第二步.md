# 阶段二第二步实施方案

## 一、当前进度判断

阶段二第一步已经完成并验证通过，当前我们不是停留在“代码能不能跑”，而是进入：

`解码端 RTHD 应该怎样部署才最合理`

已经确认成立的内容：

- `decoder_rthd_mode = none / partial / full` 可用
- `rthd_stages_decoder` 可控
- `rthd_config_encoder / rthd_config_decoder` 分离可用
- 真实 CUDA 环境前向通过

所以第二步不建议立刻再堆新模块，而是先把：

`partial decoder 到底该插在哪几层`

这个问题做扎实。


## 二、第二步的主线

阶段二第二步建议主做：

`stage-wise decoder deployment`

也就是系统比较不同解码 stage 上部署 RTHD 的效果，回答三个问题：

1. RTHD 放在 decoder 的浅层是否最有价值
2. RTHD 是否需要覆盖全部 decoder stage
3. encoder 强化以后，decoder 只做部分补充是否已经足够

这一部分很重要，因为它能把你的方法从：

`解码器也能加 RTHD`

推进成：

`RTHD 在解码恢复阶段具有可解释的最优部署规律`

这比继续往模块里塞小技巧更像一章完整方法。


## 三、为什么优先做这个

当前最稳妥的顺序不是继续加新算子，而是先做部署规律分析，原因有三点：

1. 第一版 `partial decoder RTHD` 已经具备了实验入口
2. 这一步几乎不需要再改主干代码，主要是 trainer 和配置层组合
3. 很容易形成论文里的结构性结论，而不是零散消融

建议把第二步的定位写成：

`面向结构恢复的非对称编解码部署优化`

这样第一章会更完整：

- 阶段一：模块表达增强
- 阶段二第一步：decoder 端可部署化
- 阶段二第二步：decoder 端最优部署规律


## 四、建议实验主组

默认前提：

- encoder 端继续保持你当前已经验证过的 RTHD 配置
- decoder 端使用 `decoder_rthd_mode='partial'`
- 除非特别说明，其余参数保持一致

建议主实验组如下：

### 4.1 基线组

- `E0`: `decoder_rthd_mode='none'`

意义：

- 表示只有 encoder 用 RTHD
- 这是阶段二全部比较的参考基线

### 4.2 单 stage 部署组

- `E1`: `rthd_stages_decoder=[0]`
- `E2`: `rthd_stages_decoder=[1]`
- `E3`: `rthd_stages_decoder=[2]`

意义：

- 看 decoder 哪一层单独加入 RTHD 最值钱
- 一般预期浅层更有效，因为更接近高分辨率结构恢复

### 4.3 递进部署组

- `E4`: `rthd_stages_decoder=[0,1]`
- `E5`: `rthd_stages_decoder=[0,1,2]`
- `E6`: `decoder_rthd_mode='full'`

意义：

- 看随着解码端 RTHD 覆盖范围增加，收益是持续提升还是边际递减
- 有助于判断“部分部署”是不是比“全覆盖”更优


## 五、推荐的 stage 编号解释

为了后面写论文不混乱，建议统一口径：

- `decoder stage 0`
  最靠近输出端的高分辨率恢复层

- `decoder stage 1`
  中间恢复层

- `decoder stage 2`
  更深层恢复层

如果你的代码里 stage 顺序与这里相反，那么文档和实验表里一定要提前写清：

`本章将 decoder stage 0 定义为最高分辨率解码层`

这句话非常重要，不然老师或审稿人看实验组时会误解。


## 六、预期结论方向

第二步不只是跑数，而是要争取形成下面几类结论：

### 6.1 结论 A

`解码端 RTHD 不需要全覆盖，浅层部分部署即可取得最优性价比`

如果这个结论成立，你的方法会更有“轻量化”说服力。

### 6.2 结论 B

`多轴空间建模在高分辨率结构恢复阶段更有效`

这个结论非常适合和脑肿瘤边界、细粒度区域恢复联系起来。

### 6.3 结论 C

`encoder 强语义建模 + decoder 局部多轴恢复` 比 `encoder/decoder 全对称增强` 更合理

这是第一章很值得争取的核心叙事。


## 七、如果主组结果出来后，再做两个补充组

如果上面的主实验已经跑出一个最优 decoder stage 组合，比如 `[0,1]`，那么再补两个小组就够了。

### 7.1 配置差异化补充组

在最优 `rthd_stages_decoder` 下比较：

- `D1`: encoder / decoder 共用 `rthd_config`
- `D2`: encoder 强配置，decoder 弱配置

这里的“decoder 弱配置”建议优先尝试：

- `share_weights=True`
- `cross_view_interaction=False`
- `use_local_window=False`

意义：

- 看解码端是否真的需要和编码端一样强
- 如果弱配置也能保持效果，就能进一步支撑轻量化故事

### 7.2 成本收益补充组

对比：

- `none`
- 最优 `partial`
- `full`

统计：

- 参数量
- FLOPs
- 显存占用
- 推理时间

意义：

- 让“partial 比 full 更值得”有完整证据


## 八、如果第二步结果不够理想，备选改进方向

如果发现简单的 `stage-wise deployment` 增益不明显，不建议立刻否定 decoder 端，而是转向：

`skip-guided lightweight decoder RTHD`

核心想法：

- 不在整个 decoder block 后都插 RTHD
- 只在 `skip + upsample` 融合后的特征上做一次轻量 RTHD

这样可以把解码端的 RTHD 解释为：

`针对跨层融合后的结构恢复校正`

这个方向适合作为阶段二第三步或备选线，不建议现在立刻展开。


## 九、实施建议

第二步尽量少改网络代码，多改实验入口。

建议推进顺序：

1. 先新建若干 trainer 或配置入口，分别对应 `E0-E6`
2. 先跑 `E0 / E1 / E4 / E6` 四组粗筛
3. 如果趋势明确，再补 `E2 / E3 / E5`
4. 确定最优 `partial` 组后，再做配置差异化补充实验

这样能避免一开始就把实验数量铺太大。


## 十、建议的论文表述方式

这一小节在论文里可以命名为：

`解码恢复阶段的多轴空间建模部署策略`

或者：

`面向结构恢复的部分解码 RTHD 设计`

对应的叙事逻辑可以写成：

1. 编码阶段负责长程语义提取
2. 解码阶段负责空间结构恢复
3. 因此解码端不宜简单全对称复制 encoder 设计
4. 采用部分 stage 部署的 RTHD 更符合恢复任务需求


## 十一、下一步最推荐动作

最推荐直接开始的不是继续改 `rthd_modules.py`，而是：

`为 E0-E6 建立实验入口`

如果你想继续让 Claude Code 实现，下一份提示词最适合做的是：

- 为阶段二第二步生成多个 trainer
- 或者提供一个统一 trainer，通过参数区分不同 decoder stage 部署

这一轮做完以后，你的第一章就不再只是“模块改良”，而会更像：

`模块增强 + 网络部署策略 + 结构恢复解释`

这会比单纯做 encoder 消融厚实很多。
